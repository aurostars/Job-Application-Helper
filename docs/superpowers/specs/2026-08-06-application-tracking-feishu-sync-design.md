# 投递记录与飞书多维表格同步设计

## 背景

当前插件已经具备资料管理、简历解析、表单识别、一键填充、AI 框选补填、备份导入导出和 WebDAV 同步能力，但缺少对“投递过程”本身的持续记录。用户希望插件不仅能帮助填写网申表单，还能记录自己投递过哪些网站、哪些职位、当前推进到什么阶段，并把这些记录同步到飞书中做查看和备份。

本设计新增两个相关能力：

1. 插件内的投递记录台账。
2. 将投递记录同步到飞书多维表格。

## 目标

### 业务目标

- 让用户在浏览岗位页、投递页和后续推进流程中，可以持续维护自己的投递台账。
- 让用户把投递记录同步到飞书多维表格，便于在飞书里查看、筛选、统计和备份。
- 保持插件作为主数据源，避免双向同步带来的冲突复杂度。

### 第一版目标

- 在插件中创建、编辑、删除和查看投递记录。
- 支持从当前招聘页面快速带入基础信息创建记录。
- 支持按状态、网站、关键词筛选记录。
- 支持自动同步和手动同步到飞书多维表格。
- 同步失败不影响本地保存，允许后续重试。

### 非目标

- 不做飞书反向回写插件。
- 不做插件与飞书的双向实时同步。
- 不做自动跨网站岗位去重。
- 不做复杂提醒、通知、日历联动。
- 不做招聘网站全量高精度结构化解析。

## 用户决策

以下决策已经确认，作为本设计的约束条件：

- 核心目标是“投递台账”，不是全自动留痕或提醒系统。
- 同一岗位出现在不同网站时，按多条记录分别保存，不合并。
- 插件是投递记录的唯一主数据源。
- 飞书侧只做查看和备份，不承担回写职责。
- 需要同时支持自动同步和手动立即同步。
- 飞书目标形态为多维表格，不是普通电子表格。

## 用户场景

### 场景一：浏览岗位时快速建档

用户打开 Boss、牛客、官网招聘页，点击插件后进入“投递记录”，再点击“从当前页面新建记录”。插件自动带入当前页面标题、URL、网站域名等基础信息，用户补齐公司名、岗位名或备注后保存。

### 场景二：投递后推进状态

用户完成投递后，把记录状态从“待投递”改为“已投递”，后续再更新为“笔试”“面试中”“已结束”“已拒绝”或“已录用”，并持续追加备注和联系人信息。

### 场景三：飞书查看台账

用户开启飞书同步后，每次新增或修改本地投递记录，插件自动将对应数据写入飞书多维表格。用户也可以在设置页点击“立即同步”，将待同步或失败记录重新推送到飞书。

## 方案选择

### 为什么选择“插件主数据 + 飞书镜像”

在“插件主数据 + 飞书镜像”和“双向同步”之间，本设计选择前者，原因如下：

- 现有插件已经有本地存储、备份和 WebDAV 同步模型，继续让本地存储作为真实数据源更自然。
- 飞书多维表格更适合做结构化查看与筛选，但不适合在第一版承担数据源责任。
- 双向同步会引入主键映射、冲突合并、删除传播、人工改表回写和权限异常处理，复杂度明显提升。
- 用户已明确飞书侧只做查看与备份，因此没有必要在第一版承担双向同步成本。

- 投递记录数据模型

- 投递记录工作台 UI
- 页面辅助录入能力
- 飞书同步配置与执行逻辑
- 投递记录备份与恢复支持

### 入口设计

#### 弹窗

弹窗新增“投递记录”快捷入口，用于快速进入记录工作台。

#### 侧边栏

侧边栏新增“投递记录”标签页或切换区，作为主要工作台。原因是侧边栏最适合“边看岗位页边记记录”的连续操作。

#### 设置页

设置页新增“飞书同步”分区，负责配置飞书连接、测试连接和手动同步。设置页不承担日常维护投递记录的职责。

## 数据模型

### 投递记录实体

新增 `ApplicationRecord` 数据结构，建议字段如下：

```ts
interface ApplicationRecord {
  id: string;
  siteName: string;
  siteUrl: string;
  siteHost: string;
  companyName: string;
  jobTitle: string;
  city?: string;
  department?: string;
  salaryText?: string;
  status: ApplicationStatus;
  appliedAt?: string;
  deadline?: string;
  notes?: string;
  resumeName?: string;
  contactName?: string;
  contactInfo?: string;
  createdAt: string;
  updatedAt: string;
  events: ApplicationEvent[];
  feishuSync?: FeishuSyncState;
  deletedAt?: string | null;
}
```

### 状态枚举

第一版控制在少量固定状态：

```ts
type ApplicationStatus =
  | '待投递'
  | '已投递'
  | '笔试'
  | '面试中'
  | '已结束'
  | '已拒绝'
  | '已录用';
```

### 状态事件

状态事件用于记录每次推进过程，供详情页时间线使用：

```ts
interface ApplicationEvent {
  id: string;
  type: 'status_change' | 'note_added' | 'created' | 'sync';
  createdAt: string;
  summary: string;
  detail?: string;
}
```

### 飞书同步状态

```ts
interface FeishuSyncState {
  enabled: boolean;
  recordId?: string;
  lastSyncedAt?: string;
  status: 'idle' | 'pending' | 'syncing' | 'synced' | 'error';
  lastError?: string;
}
```

### 存储结构

第一版建议在 `chrome.storage.local` 中新增独立键，而不是把投递记录直接塞进 `userProfile`：

- `applicationRecords`
- `feishuSyncConfig`

原因如下：

- 投递记录与个人资料生命周期不同。
- 投递记录更新频率更高。
- 单独维护更利于分页、筛选、后续迁移和同步扩展。
- 避免把 `UserProfile` 膨胀成难以维护的超级对象。

## 飞书同步配置

### 配置实体

```ts
interface FeishuSyncConfig {
  enabled: boolean;
  appToken: string;
  tableId: string;
  viewName?: string;
  autoSync: boolean;
}
```

第一版默认只支持一个飞书多维表格目标，不支持多张表切换。

### 字段映射

飞书多维表格建议建立如下字段：

- `记录ID`
- `岗位名称`
- `公司`
- `网站`
- `链接`
- `域名`
- `城市`
- `部门`
- `薪资`
- `状态`
- `投递时间`
- `更新时间`
- `截止时间`
- `简历版本`
- `联系人`
- `联系方式`
- `备注`
- `同步状态`

字段类型建议：

- `记录ID`：文本，必要时隐藏
- `岗位名称`：单行文本
- `公司`：单行文本
- `网站`：单行文本
- `链接`：URL
- `状态`：单选
- `投递时间`、`更新时间`、`截止时间`：日期时间
- `备注`：多行文本

`记录ID` 是插件和飞书记录之间的稳定映射字段。第一版以它为准，不依赖“岗位名称 + 公司”做模糊匹配。

## 页面辅助录入

### 录入方式

第一版提供“从当前页面新建记录”能力，但只做轻量提取，不承诺对所有招聘站点都能完整解析。

### 提取内容

从当前页面提取以下候选信息：

- 页面标题
- 当前 URL
- 域名
- 页面内可能的岗位名文本
- 页面内可能的公司名文本

### 使用方式

用户点击“从当前页面新建记录”后，先展示一张确认表单，自动填入可识别字段，用户确认或修正后再保存。本地永远以用户确认后的内容为准。

### 降级策略

如果无法识别岗位名或公司名，至少保留：

- `siteUrl`
- `siteHost`
- 页面标题

其余字段允许用户手动补充，不把识别失败视为保存失败。

## 同步策略

### 总原则

- 本地保存优先于远端同步。
- 远端同步失败不能回滚本地保存。
- 自动同步是增强能力，不是主流程依赖。

### 自动同步触发时机

以下操作成功写入本地后，如果飞书同步已启用且自动同步已开启，则触发同步：

- 新建记录
- 编辑记录
- 修改状态
- 删除记录

### 手动同步

设置页提供两类手动同步操作：

- `立即同步`：同步全部待同步和失败记录
- `重试失败记录`：仅重试失败项

如果实现成本控制需要收敛，第一版只保留一个 `立即同步` 按钮也可以，但内部逻辑仍以“只同步非最新状态的记录”为准。

### 单条同步流程

1. 读取本地记录。
2. 判断该记录是否已有 `feishuSync.recordId`。
3. 如果没有，则在飞书表中新建记录。
4. 如果已有，则更新对应记录。
5. 成功后回写本地同步状态。
6. 失败后写入错误信息，并保留待重试状态。

### 删除策略

第一版不直接删除飞书中的记录，而是采用软删除策略：

- 本地删除时，将记录标记为 `deletedAt`
- 飞书同步时把 `同步状态` 或 `状态` 更新为“已删除”或保留原状态并追加删除标记

选择软删除而不是真删的原因：

- 更安全，避免误删飞书数据
- 便于后续排查同步错误
- 不需要第一版处理“飞书已经删除但本地还引用 recordId”的复杂异常

## 错误处理

### 本地保存失败

本地保存失败直接提示用户，视为操作失败，不触发远端同步。

### 飞书同步失败

飞书同步失败时：

- 当前记录仍保存成功
- 记录的 `feishuSync.status` 标为 `error`
- 保存错误消息到 `lastError`
- 在 UI 中展示“同步失败，可重试”

### 鉴权或配置错误

如果配置缺失、权限不足、表不存在或字段不匹配：

- 设置页显示明确错误
- 自动同步停止继续重试，避免每次编辑都报错
- 保留手动测试连接入口

### 网络错误

网络错误视为暂时失败：

- 不影响本地
- 保持待重试
- 用户下次手动同步时继续尝试

## 备份与恢复

### 导出

现有备份结构需要纳入以下数据：

- `applicationRecords`
- `feishuSyncConfig`

### 导入

导入时恢复本地投递记录和飞书同步配置，但不主动触发飞书全量重写。是否重新推送远端，交给用户手动执行“立即同步”。

### 与 WebDAV 的关系

投递记录和飞书同步配置都应纳入现有业务备份数据，由现有 WebDAV 机制统一同步。换句话说：

- WebDAV 负责跨设备同步插件本地状态
- 飞书负责对投递记录做结构化查看镜像

两者职责不同，不互相替代。

## 接口边界

### 记录服务

记录服务负责：

- 新建、更新、查询、删除投递记录
- 维护 `updatedAt`
- 写入事件流
- 标记同步状态

记录服务不负责：

- 飞书 API 调用细节
- 页面 DOM 识别逻辑

### 飞书服务

飞书服务负责：

- 测试连接
- 新建飞书记录
- 更新飞书记录
- 映射请求与响应字段

飞书服务不负责：

- 本地业务校验
- 冲突合并
- UI 状态控制

### 页面提取服务

页面提取能力负责：

- 从当前页面提取最小可用信息
- 返回候选字段

它不直接保存记录，避免 content script 变成业务入口。

## 已确认的取舍

- 第一版选择多维表格而不是电子表格。
- 第一版不做双向同步。
- 第一版不做真实删除远端记录。
- 第一版允许识别不完整，但必须保证最小可创建记录。
- 第一版把飞书同步视为增强能力，不能阻塞本地主流程。

## 待进入实现规划的问题

以下问题不再影响设计方向，但会在实现规划阶段细化：

- 飞书连接采用用户手填参数，还是后续接入正式授权流程。
- “飞书同步”设置是并入现有 `DataSyncSettings`，还是拆为单独设置卡片。
- 投递记录工作台是直接复用当前侧边栏页面，还是做 tab 切换结构。
- 页面辅助录入第一版优先识别哪些站点。

## 结论

本设计选择以插件为唯一主数据源，新增投递记录台账，并将其同步到飞书多维表格作为结构化镜像。第一版重点是先把“记录、查看、筛选、推进状态、稳定同步”做好，而不是追求全自动识别或双向协同。这样能在保持当前插件架构清晰的前提下，快速扩展出一个真正有持续使用价值的网申过程管理能力。

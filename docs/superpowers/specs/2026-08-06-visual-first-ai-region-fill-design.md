# 视觉优先 AI 框选补填设计稿

## 背景

当前 `AI 框选补填` 已具备基础能力，但主链路仍然以 DOM 字段识别和文本型 `AI_FILL_SECTION` 为核心。对于字段 `name`、`label`、`placeholder` 语义较差、页面组件封装较重、字段真实含义主要依赖视觉排版表达的页面，现有链路的识别准确率存在明显上限。

本设计稿定义一条仅服务于 `AI 框选补填` 的全新链路：以区域截图和区域内控件几何信息为主输入，由视觉模型完成单次重推理，再由本地 DOM 锚点负责安全写回。该链路优先追求识别准确率，不追求最短耗时，不影响现有 `快速填充` 与 `AI 扫描填充` 的行为。

## 目标

- 为 `AI 框选补填` 增加一条视觉优先的补填链路，提升复杂页面上的字段理解准确率。
- 在一次视觉推理中同时完成字段理解、资料匹配、结果输出，减少中间状态漂移。
- 严格约束 AI 输出只能映射到本地已采集的可写控件，禁止模型自由生成目标字段。
- 保持现有 `快速填充`、`AI 扫描填充` 和文本型 `AI_FILL_SECTION` 主链路不变。

## 非目标

- 不改造 `AI 扫描填充` 为视觉优先链路。
- 不在没有视觉模型配置时自动降级到旧的 `AI_FILL_SECTION`。
- 不实现多次推理或“先识别后再次匹配”的两段式多模态流程。
- 不在第一版中支持跨区域、多截图拼接或整页视觉扫描。
- 不在第一版中暴露复杂调试 UI、逐字段解释面板或人工确认步骤。

## 用户体验

用户从 popup 点击 `AI 框选补填` 后，进入当前页面的框选模式。完成框选后，插件将采集选区截图和选区内可写控件列表，并调用支持视觉输入的 AI 模型做一次重推理。若成功，系统直接将结果写回页面；若部分字段无法可靠识别或写入，提示真实补填数量；若视觉模型未配置、截图失败或模型返回无效结构，则整单失败并给出明确错误提示。

## 核心原则

### 视觉优先

该链路中，视觉模型负责“看懂当前区域的表单语义和版面关系”。DOM 不再负责主导字段语义判断，只负责提供可写入目标集合、位置锚点和最终写回能力。

### 单次重推理

字段理解、用户资料匹配和结果输出应在一次重视觉推理中完成，避免将“识别字段”和“匹配资料”拆为两次 AI 调用，减少上下文丢失和中间误差传播。

### 受约束匹配

即使 AI 同时负责字段理解和资料匹配，模型也只能：

- 从本地提供的用户资料中选择值；
- 将值映射到本地提供的 `controlId`；
- 在不确定时返回空值；
- 不得生成不存在于资料中的新内容；
- 不得返回不在本地控件清单中的字段标识。

### 安全落地

AI 结果不直接拥有写回权限。本地必须在写回前完成结果结构校验、目标控件校验、可选项校验和类型兼容性过滤。

## 范围

本设计只应用于：

- popup 中现有 `AI 框选补填` 按钮；
- 用户在内容页中框选出的单个区域；
- 支持图片输入的视觉模型。

本设计不应用于：

- `快速填充`；
- `AI 扫描填充`；
- 任何未配置视觉模型的使用场景。

## 架构概览

整条链路分为五层：

1. `popup` 入口层：校验视觉模型能力，启动框选模式。
2. `content` 交互采集层：维持框选交互，采集截图与控件清单。
3. `background` 编排层：读取资料、构造多模态 prompt、调用视觉模型、清洗结果。
4. `prompt` 层：定义多模态输入和严格 JSON 输出协议。
5. 写回层：根据本地控件锚点将结果落到真实表单元素。

## 模块划分

### popup 入口层

职责：

- 用户点击 `AI 框选补填` 时触发启动逻辑；
- 读取当前 AI 配置；
- 校验当前模型是否支持图片输入；
- 若不支持，直接提示并阻止进入框选模式；
- 若支持，发送 `START_AI_REGION_FILL` 消息。

约束：

- 不负责截图、不负责字段识别、不负责写回。
- 保留现有按钮名称，不新增按钮。

### content 交互采集层

职责：

- 复用现有框选交互体验；
- 用户完成框选后，采集选区截图；
- 采集选区内全部可写控件的轻量 DOM 信息；
- 为每个控件分配本次会话唯一 `controlId`；
- 将截图和控件清单发送给 background；
- 接收结果后执行写回；
- 展示处理中、已终止、成功、部分成功、失败等状态提示。

建议新增独立模块：

- `src/content/visualRegionFill.ts`

作用：

- 将现有 `AI 框选补填` 的视觉优先链路从 `src/content/index.ts` 中拆出；
- 降低主文件复杂度；
- 方便单独编写测试与维护。

### background 编排层

职责：

- 接收视觉区域补填请求；
- 校验当前模型是否支持视觉输入；
- 读取用户资料；
- 构造视觉多模态 prompt；
- 调用视觉模型；
- 校验模型返回结构；
- 将结果整理为可写回映射；
- 支持请求级终止。

约束：

- 不直接操作 DOM；
- 不直接进行页面写回；
- 不复用文本型 `handleAIFillSection()` 主逻辑。

建议新增独立 handler：

- `handleVisualRegionFill()`

### prompt 层

职责：

- 构造视觉区域补填的系统提示词与用户提示词；
- 明确视觉输入、控件列表和用户资料的含义；
- 定义严格 JSON 输出格式；
- 限制模型只能给已提供的 `controlId` 返回值。

建议新增方法：

- `buildVisualRegionFillPrompt()`

### 写回层

职责：

- 根据 `controlId` 找到真实元素；
- 调用已有 `formFiller.fillElementValues()` 或等价能力执行写回；
- 复用已有输入框、下拉框、组合框、日期区间等写值策略；
- 统计成功/失败数量。

## 数据采集设计

### 区域截图

截图是视觉模型的主输入。截图必须严格对应用户框选区域，包含区域内控件、标签、相邻文本和版面结构，不需要包含整页上下文。

建议字段：

- `base64`
- `mimeType`
- `width`
- `height`

### 控件清单

每个控件必须带最小可写回锚点信息与最小可解释上下文，建议包含：

- `controlId`
- `tagName`
- `inputType`
- `role`
- `label`
- `name`
- `placeholder`
- `options`
- `rect`
- `contextText`

其中：

- `controlId` 是本次请求生命周期内的主键；
- `rect` 用于帮助模型理解“视觉中哪个框对应哪个控件”；
- `options` 用于限制可选字段返回值；
- `contextText` 用于补充附近文本上下文。

### 控件标识策略

第一版采用 `controlId + rect` 双轨方案：

- `controlId` 作为写回主键；
- `rect` 作为视觉理解的辅助定位依据；
- content 写回时优先用 `controlId` 找元素；
- 若元素因页面重渲染失活，可做一次基于近邻坐标的有限重定位；
- 不采用纯 `index` 或纯坐标方案作为主锚点。

## 消息协议

### 现有启动消息

保留现有启动消息：

```ts
{ type: 'START_AI_REGION_FILL'; payload?: null }
```

含义保持不变：进入框选模式。

### 新增主消息

content 在用户完成框选后，发送新的视觉主消息：

```ts
{
  type: 'AI_FILL_VISUAL_REGION',
  payload: {
    requestId: string;
    domain: string;
    image: {
      base64: string;
      mimeType: 'image/png';
      width: number;
      height: number;
    };
    controls: Array<{
      controlId: string;
      tagName: 'input' | 'textarea' | 'select';
      inputType?: string;
      role?: string;
      label: string;
      name: string;
      placeholder: string;
      options: string[];
      rect: {
        left: number;
        top: number;
        width: number;
        height: number;
      };
      contextText: string;
    }>;
  };
}
```

设计原则：

- `image` 负责让模型“看懂”区域；
- `controls` 负责限制模型只能在已知目标内分配结果；
- `requestId` 复用现有终止逻辑；
- 该消息与 `AI_FILL_SECTION` 解耦，避免混淆文本补填与视觉补填。

### 终止消息

继续复用：

```ts
{ type: 'CANCEL_AI_FILL', payload: { requestId: string } }
```

### 返回结构

background 返回成功结果时，建议使用以下结构：

```ts
{
  success: true,
  data: {
    mappings: Array<{
      controlId: string;
      fieldMeaning: string;
      matchedProfilePath: string;
      value: string;
    }>;
  };
}
```

本地实际落地时：

- `controlId` 必须存在；
- `matchedProfilePath` 必须指向允许读取的资料路径；
- `value` 必须与资料中的真实值一致；
- 若控件存在 `options`，则 `value` 必须命中可选项。

第一版不要求对用户展示 `fieldMeaning` 或 `matchedProfilePath`，但建议保留在内部结构中，便于调试和结果校验。

## AI 匹配策略

### 是否使用 AI 进行资料匹配

是。字段理解和资料匹配都由 AI 在同一次推理中完成。

原因：

- 复杂页面中，字段真实语义常依赖视觉版面关系，而非单个 label；
- 某些重复区块需要 AI 同时理解位置、结构和用户资料内容；
- 将识别和匹配拆成两步会增加中间漂移和误差积累。

### 受约束匹配规则

虽然 AI 负责匹配，但必须遵守以下规则：

- 只能使用提供的用户资料内容；
- 不得编造新值；
- 不得生成不存在的 `controlId`；
- 不得输出不在 `options` 中的值；
- 不确定时必须返回空值，不允许猜测。

### 推荐输出思路

模型在同一次推理中完成：

1. 识别控件语义；
2. 判断其最匹配的资料路径；
3. 输出最终可写回值。

这比“先识别字段，再让本地规则匹配”更适合本设计的准确率优先目标。

## Prompt 设计

### 输入

模型输入包括：

- 当前网站域名；
- 用户框选区域截图；
- 区域内可写控件清单；
- 每个控件的矩形坐标和上下文；
- 完整用户资料。

### 规则

系统提示词必须明确：

- 截图是主语义输入；
- 控件清单是唯一允许输出目标；
- 只能从资料中选择已有值；
- 不确定时返回空字符串；
- 只能返回严格 JSON。

### 输出

模型输出应被限制为结构化 JSON，不允许输出 Markdown、解释性文字或额外字段。

## 错误处理

### 启动前拦截

以下情况直接阻断，不进入推理：

- 未配置 AI；
- 当前模型不支持图片输入；
- 当前页面受限，无法操作；
- 用户未完成框选；
- 选区内没有可写控件。

这些错误直接向用户显示明确提示，不做自动降级。

### 采集阶段失败

包括：

- 截图失败；
- 控件清单采集失败；
- 选区内控件为空；
- 控件几何信息严重异常。

处理策略：

- 截图失败：整单失败；
- 控件清单为空：整单失败；
- 单个控件异常：跳过该控件，其余控件继续。

### 模型推理失败

包括：

- 接口超时；
- 非 JSON 返回；
- 结构不符合约定 schema；
- 返回了不存在的 `controlId`；
- 返回值与控件约束不兼容。

处理策略：

- 非 JSON 或整体结构无效：整单失败；
- 单项结果非法：丢弃该项；
- 最终没有任何有效映射：整单失败；
- 存在部分有效映射：允许部分补填。

### 写回失败

包括：

- 目标元素丢失；
- 页面重渲染导致控件失效；
- 特殊组件拒绝写入；
- 下拉、组合框或日期控件交互失败。

处理策略：

- 单字段失败不影响整单；
- 统计成功和失败数量；
- 最终向用户展示真实补填结果。

## 回退策略

### 允许的回退

- 单个控件写回失败时跳过该控件；
- 元素失活时尝试一次有限重定位；
- 模型仅返回部分有效结果时执行部分补填。

### 不允许的回退

- 无视觉模型时自动退回旧 `AI_FILL_SECTION`；
- 截图失败时偷偷降级为纯 DOM 补填；
- 模型不确定时仍强行填写。

本设计选择了准确率优先，因此不允许以隐式降级换取“看起来还能运行”的假成功。

## 成功与失败判定

建议采用以下判定规则：

- 截图失败：整单失败；
- 模型调用失败：整单失败；
- 模型成功但无有效映射：整单失败；
- 模型成功且部分映射有效：部分补填；
- 写回阶段部分失败：部分补填并提示数量；
- 写回阶段全部成功：成功。

最终提示文案必须基于真实结果，例如：

- `AI 识别完成，成功补填 6 项，2 项未能写入`
- `当前模型不支持图片识别，请在设置中切换到支持视觉输入的模型`
- `当前选区内没有可补填的输入控件`

## 与现有功能的关系

### 快速填充

不变。继续使用现有规则链路。

### AI 扫描填充

不变。继续使用整页扫描后按组调用 `AI_FILL_SECTION` 的链路。

### AI 框选补填

升级为新的视觉优先链路。名称保持不变，但内部实现不再依赖现有文本型 `AI_FILL_SECTION` 主逻辑。

### AI_FILL_SECTION

继续服务现有扫描链路，不承载视觉优先框选补填职责。

## 建议文件落点

- `src/content/index.ts`
  - 保留消息分发和入口挂接；
- `src/content/visualRegionFill.ts`
  - 承载截图采集、控件采集、视觉补填调用与状态管理；
- `src/background/index.ts`
  - 新增 `AI_FILL_VISUAL_REGION` case 与 `handleVisualRegionFill()`；
- `src/services/llm/prompts.ts`
  - 新增 `buildVisualRegionFillPrompt()`；
- `src/shared/types.ts`
  - 新增视觉补填消息类型、payload 类型、返回结构类型；
- 可选新增 `src/services/llm/visualFill.ts`
  - 用于承载视觉返回结果校验与结构化解析。

## 第一版不做项

为了控制范围，第一版明确不做：

- 无视觉模型时自动降级；
- 多次推理；
- 用户人工确认每个字段；
- 跨区域拼接截图；
- 整页视觉扫描；
- 字段级解释面板；
- 写回前的人工审阅步骤；
- 复杂调试视图和开发者面板。

## 验收标准

第一版完成后，应满足以下结果：

- 用户可以从现有 `AI 框选补填` 按钮进入视觉优先链路；
- 未配置视觉模型时，入口会被明确阻断；
- 框选完成后，系统能采集截图和控件清单；
- background 能调用视觉模型完成一次重推理；
- 模型返回结果经过本地校验后才能写回；
- 系统能正确统计成功、失败和部分成功数量；
- `快速填充` 与 `AI 扫描填充` 行为不受影响；
- 现有文本型 `AI_FILL_SECTION` 链路不被破坏。

## 风险

- 不同模型的图片输入格式和多模态能力差异较大；
- 某些页面可能存在截图权限、滚动容器裁切或坐标换算问题；
- 自定义组件较多的网站可能仍然存在写回兼容性问题；
- 单次重视觉推理的时延和成本较高。

## 结论

本设计将 `AI 框选补填` 独立升级为一条视觉优先、单次重推理、准确率优先的多模态补填链路。其关键点在于：由视觉模型完成字段理解与资料匹配，由本地 DOM 锚点负责安全落地，不做隐式降级，不影响现有其他填充功能。
